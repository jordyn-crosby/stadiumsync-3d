# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

StadiumSync 3D is a static, single-page web app for designing stadium LED light shows for one venue (Jordan-Hare — there is no venue picker): a zone-based pattern designer with per-seat painting, a section library for custom sections, a timeline/cue sequencer, a real-time 3D stadium preview, and a project export view. The 3D stadium (Jordan-Hare, the only venue) and its 24,778 per-seat LEDs are ported from the team's Unity simulation (`../arenalighting-fall2026/stadium copy`). There is no build step, no package manager, and no test suite — everything is plain HTML/CSS/JS served as static files.

## Running the app

There is no build/install/test command. Serve the directory with any static file server and open it in a browser (WebGL required):

```bash
python3 -m http.server 8000
```

Then visit `http://localhost:8000`. Opening `index.html` directly via `file://` will break some features, so always serve it.

## Architecture

### File layout

- `index.html` — the entire application: markup, CSS (as `:root` custom-property design tokens), and application logic, all inside **one large IIFE** in a single `<script>` block near the bottom of the file (~2200 lines of JS). There is no module system and no separate `app.js`.
- `stadium3d.js` — the 3D stadium renderer, also a single IIFE, exposing one global: `window.Stadium3D.createStadium3D(canvas, opts)`. It's loaded as `stadium3d.js?v=<date>`: bump that `?v=` in `index.html` whenever you change the file, or browsers keep running their cached copy.
- `assets/jordan-hare/` — **generated** venue assets: `stadium.glb` (meshopt-compressed), `leds.json` (per-LED position/zone/row/col/section), `cameras.json` (Unity camera presets), `show-first-demo.{json,bin}` (Spring '25 demo show). Don't hand-edit; regenerate with the pipeline in `tools/` (see `tools/README.md`).
- `tools/` — offline, one-time Unity → web export pipeline: `unity/StadiumWebExporter.cs` (Unity Editor script), `build_web_assets.py` (stdlib Python + `sips` + `npx gltfpack`), `zone_map.json` (which Unity sections belong to which of the 11 zones). Not used at runtime.
- `vendor/` — vendored third-party libraries loaded via plain `<script>` tags before `stadium3d.js`: `three.min.js` (r128), `OrbitControls.js`, `libs/meshopt_decoder.js` + `loaders/GLTFLoader.js` (r128, for the compressed `stadium.glb`), and a minimal postprocessing pipeline (`EffectComposer`, `RenderPass`, `ShaderPass`, `UnrealBloomPass` + `CopyShader`/`LuminosityHighPassShader`) used for LED bloom.

### State management

All app state lives as plain module-scoped `var` declarations inside the `index.html` IIFE (venues, current selection, pattern library, timeline tracks/cues, music-sync state, etc.) — there is no state library and no backend. Reloading the page resets everything to the hardcoded seed data (`venues` array, `patternLibrary` array, etc. defined near the top of the script), except for saved items:

- **Saved items (IndexedDB).** `savedStore` in `index.html` wraps an IndexedDB database `stadiumsync` (version 4) with five object stores: `patterns` (whole pattern objects — user-created ones, plus edited copies of built-ins, keyed by `id`), `songs` (imported audio files as Blobs with name/size), `sections` (custom sections: `{id, name, sections, createdAt}`, `sections` being seating-section names from `leds.json`) and `timelines` (named timelines: `{id, name, venueId, cues, songId, marks, customTracks, keepDefault, customOnTop, savedAt}` — the cues, the song they were built to and that song's bookmarks, plus which custom sections are on it and how they stack; older saves without the last three open with just the default sections) and `workspace` (one record, key `designer`: Designer zone on/off and sliders plus seat paint groups and per-LED assignments, saved by `saveWorkspaceSoon` after every change; saved seat paint waits in `pendingPaintSeats` until the Designer's LEDs load). Saves stay in that browser on that computer. On startup `restoreSavedPatterns` merges saved patterns over the seed library, `restoreCustomSections` loads custom sections, `restoreWorkspace` reapplies Designer settings and `restoreSavedSongs` lists songs and reloads the last one played (its id is in `localStorage` as `stadiumsync.lastSongId`); after all of them, `restoreSavedTimelines` reopens the last saved/opened timeline (`stadiumsync.lastTimelineId`). Timelines are saved explicitly (Save button above the Timeline transport, name required); `renderTimeline` calls `updateTimelineSaveState` to show "Unsaved changes", and opening another timeline or starting a new one confirms before discarding them. The open timeline's name becomes the Export project name (`#project-name`). `builtInPatterns` keeps the untouched seed copies for "Reset to original". Every `savedStore` call resolves rather than rejects, so the app still runs where IndexedDB is unavailable.
- **Backups.** The Export page's "Back up or move your work" panel downloads one `.json` file (`format: 'stadiumsync-backup'`, built by `buildBackup`) with the user's pick of saved timelines, patterns they made or changed (`userPatterns`), custom sections, Designer zones and seat paint (seat paint as `[first seat, count, group]` runs), preferences and songs (base64 audio, on by default; `songRefs` always lists them so timelines can match songs already in the other browser). `importBackup` merges one in: items with the same id or name are replaced, and the backup's ids are remapped onto them in its timelines. Anything new that users can save should be added to both.

Views are swapped by toggling visibility of top-level sections and re-running per-view `render*()` functions (e.g. `renderLayers`, `renderInspector`, `renderPatternGrid`, `renderTimeline`, `renderExportView`) rather than any virtual-DOM diffing — each one rebuilds its section's `innerHTML` from current state.

### Custom sections

The Sections page (`#section-view`) builds custom sections by clicking seating sections (or pressing on one and dragging, which adds every section the cursor crosses; the press is caught in the capture phase so OrbitControls doesn't turn the stadium) on a third, lazily created stadium instance (`ensureSectionStadium`; picked seats are drawn with `setLedOverride`). Clicking a section in the "Your sections" list checks it (`checkedSectionIds`, with Select all) and opens it in the editor; the buttons under the list add the checked sections to the Timeline, skipping any already on it, or take them off. A custom section is on the Timeline as a track whose cues use the track id `custom:<section id>` (`trackLabel` gives its display name); `timelineTracks()` — not `timelineTracksByVenue` — is the list of tracks the Timeline shows and plays. Per timeline, `timelineLayout` holds `customTracks` (highest priority first), `keepDefault` (untick to hide the four default tracks; their cues are kept but don't play) and `customOnTop` (on seats a custom and a default section share, which wins while both have a cue playing). In the Show, default tracks still drive zones via `updatePreviewStadium`; custom sections are lit per seat by `fillCustomSectionLayer` (called from `applyShowOverrides`, under seat paint), using the shared pattern math on each seat's own zone-grid position (`getLedData().zoneCol/zoneRow/around/zoneCols/zoneRows`) so they line up with the zones around them. Music "Flash on big hits" only applies to default sections.

### The shared LED math contract

`computeDotBrightness(pattern, col, t, totalCols, row, totalRows, around)` and `getDotColor(pattern, col, row, totalCols, totalRows)` (defined in `index.html`) are the single source of truth for what a pattern looks like at a given time/position. They are used to animate:
- the 2D LED matrix previews (zone inspector, timeline cues and scrubbing, and the hover preview on pattern cards in the library and under the timeline — `drawSwatchPreview`),
- the 3D stadium view — these two functions are passed **into** `stadium3d.js` via `createStadium3D(canvas, { computeDotBrightness, getDotColor })` rather than being reimplemented there. In 3D, `col`/`row`/`totalCols`/`totalRows` come from each LED's zone grid in `leds.json`, not from `LED_COLS`/`LED_ROWS` (flipped in `loadVenue` so row/col 0 is the top left as seen from the field, matching the 2D previews — `leds.json` itself counts from the front row, right to left), and the optional `around` (0–1, the LED's angle about the stadium center, precomputed per zone in `loadVenue`) lets stadium-spanning motions like The Wave (`motion: 'crowd-wave'`) travel around the whole bowl; callers without it (2D grids) fall back to column position.

The four stadium-wide patterns (Checkerboard + Streak, Sine Wave Split, Circulating Wave, Radar Sweep) color dots by position on the venue's 400×300 map instead: their math lives in `checkerboardStreakAt`/`sineWaveSplitAt`/`circulatingWaveAt`/`radarSweepAt` (dispatched by `venueWideColorAt`), wrapped per zone by the `get*Color(slug, …)` functions.

User-made (custom) patterns get extra inspector controls (`bindCustomPatternControls`; built-ins keep only color/intensity/band width/frequency): a motion from `CUSTOM_MOTIONS` (adds `wipe` and `ripple` to the built-in motions), an optional `direction` (for `wave`/`wipe`, plus `bounce` for `wave`; `outward`/`inward` for `ripple`), up to four `colors` with a `colorLayout` (`stripes`/`bands`/`gradient`, scattered when unset) and a `dimLevel` (how bright "off" dots stay, 0–60%, default 6). All of it is read by `computeDotBrightness`/`getDotColor`, so it shows the same in 2D and 3D.

When changing pattern rendering logic, change it in these two functions only — do not add parallel logic inside `stadium3d.js`, or the 2D and 3D views will disagree. The same goes for the seat-level effects (seat paint, demo show, music gain): their color math lives in `index.html` (`paintedSeatRgb`, `applyDemoShowFrame`, `applyMusicLedGain`) and is handed to the renderer as buffers.

### `stadium3d.js` renderer

- `loadVenue(venue)` loads `venue.model = {glb, leds, cameras}` and returns a Promise. Assets are cached at module level, so the Designer and Preview instances fetch/parse them once. The stadium mesh and all LEDs share one coordinate space (Unity world space mirrored x → −x).
- All 24,778 LEDs are **one `InstancedMesh`** (unlit spheres, per-instance color; the all-white vertex-color attribute is required in r128 — see the comment in `buildLedMesh`). Venue zones are matched to `leds.json` zones **by name**, so `zoneData[].name` must match `tools/zone_map.json`.
- Each frame, LED color = (seat override if masked, else the zone pattern color written by `setZoneFrame`) × per-LED gain, with unlit LEDs of the `highlightZone` zone brightened. LED colors are kept ≤ 1 (clipping shifts hue, e.g. blue → cyan); bloom threshold is set so lit LEDs glow but the stadium texture doesn't.
- API: `loadVenue`, `setZoneFrame`, `highlightZone`, `setLedOverride(colors, mask)`, `setLedGain(gain)`, `getLedData()` (also each LED's zone-grid `zoneCol`/`zoneRow`/`around`, as `setZoneFrame` uses them), `pickLed(clientX, clientY)` (manual ray/sphere test → `{index, rowId, section, zone}`), `getCameraPresets`, `setCameraPreset`, `setCameraMode('orbit'|'aerial'|'free', options)` (for aerial, `{fit:true}` pulls back to keep the whole stadium in frame at every point of the circle, measured from the model's vertices, instead of `cameras.json`'s distance, and `{snap:true}` starts on the circle instead of gliding in — the Designer opens this way), `setAutoOrbit`, `setTimeOfDay`, `setFogDensity`, `onResize`, an `onFrame` hook setter, and `dispose`.
- `index.html` creates the Designer, Preview and Sections instances lazily, the first time each view is opened (`ensureDesignerStadium` / `ensurePreviewStadium` / `ensureSectionStadium`), and `setActiveStadiumView` calls `setActive(true|false)` on view switches — an inactive instance cancels its `requestAnimationFrame` loop entirely. Any code touching `designerStadium`/`previewStadium` must null-check them. Don't add always-on animation loops for hidden UI; the only per-frame work should belong to the visible view.

### Music sync

The Preview view can drive pattern playback from an uploaded audio file via the Web Audio API (`musicAudioCtx`/`musicAnalyser`/`musicFreqData`), with rolling per-band ceilings and separate kick/chant onset-detection histories used to trigger beat-synced flashes. This logic is entirely inline in `index.html` near the bottom of the script. Alongside it, `computeAudioPeerBands` ports the Unity sim's `AudioPeer` (8 octave bands with decay buffers and running-max normalization) to drive the per-seat Linear / Random / Amplitude music modes, and the Spring '25 demo show plays from `assets/jordan-hare/show-first-demo.*` on the Preview transport clock.

The Timeline reuses the loaded song too: `buildWaveform` decodes it once (via `OfflineAudioContext`) into 10ms peak frames for the waveform strip drawn under every track, and `detectBeatHits` finds onset times (log-energy flux, bass-weighted), plus the subset of "big beats" (hits ≥60% as strong as the strongest within ±2s). With the "Snap to beats" toggle on, dropped/moved/resized cue edges snap to big beats from 24px away, or to any hit from 8px. The selected cue's popover (`fillCuePopover`) switches its pattern (`setCuePattern`, also done by clicking a card in the Patterns strip while a cue is selected; applies to linked "On every section" copies too) and copies it onto another section at the same time ("Copy to section"); Option/Alt-dragging a cue drops an unlinked copy anywhere, on any section (`duplicateCue`). A cue can also recolor its pattern without touching the library: `cue.recolor` (only the changed `color`/`colors`/`bgColor`/`trimColor`) is laid over a copy of the pattern by `cuePattern(cue)`, which every place that draws or plays a cue must use instead of `findPattern(cue.pattern)`. Recoloring applies to linked copies and, unless unticked, to other sections' cues playing the same pattern at an overlapping time (`matchingCues`); switching a cue's pattern drops its recolor. A cue's `brightness` (0–100, from the popover's slider; absent means 100) becomes `level` (0–1) on the `cuePattern` copy — an output gain that `setZoneFrame`, `fillCustomSectionLayer` and the dot previews multiply in after the pattern math (`patternLevel`), so 0% is dark rather than the 30% floor. Moved, Option-drag-copied and dropped cues slot in among their track's other cues rather than overwriting them (`placeAmongCues`): with the pointer over a cue they go right after it, and in a gap they butt up against the neighbours they overlap and are shortened to fit when the gap is narrower; holding Shift keeps the free placement, which replaces what it covers (`carveOutCue`). Several cues can be selected (Shift/Cmd-click, a box dragged over empty track space, Cmd/Ctrl+A; `selectedCues`, read through `currentSelection()`, with `selectedCue` the one the popover edits) and grouped (Cmd/Ctrl+G, or the popover's Group): grouped cues share a `unit` id (saved with the timeline), are selected together, and move, Option-drag-copy and delete together, each on its own section; `tidyUnits` drops groups left with one cue. This `unit` is separate from `group`, which links "On every section" copies. Cue edges always snap first to the playhead and to the song's bookmarks (12px). The playhead is moved by pressing/dragging on the Timeline ruler; clicking its knob (without dragging) toggles a bookmark at the playhead (`marksBySong`, in memory per song). Bookmarks are `.wave-mark` elements in the waveform strips; hovering one shows a × and clicking deletes it. The knob is outlined, and filled while the playhead sits on a bookmark.

## Conventions to preserve

- No new build tooling, package manager, or module bundler — keep the app dependency-free and directly servable as static files.
- New third-party code goes in `vendor/` as a plain script, loaded via a `<script>` tag in `index.html`, consistent with the existing Three.js/postprocessing setup.
- Design tokens (colors, spacing, radii) are CSS custom properties on `:root` in `index.html` — reuse them rather than hardcoding new values. The look follows auburn.edu: light grey-white surfaces (`--bg` `#e7e9ec`, white panels), Auburn navy `#0b2341` (`--primary`) for text and buttons, and Auburn orange `#e86100` (`--accent`; `#cc4e0b` as `--accent-text` for orange text on white) as the accent for selection, the sidebar's top rule and the playhead. Don't make the chrome all navy. Night mode (the moon toggle in the sidebar footer, remembered in `localStorage` as `stadiumsync.nightMode` and applied by a small `<head>` script before first paint) is `:root[data-theme="night"]`, which redefines the same tokens with dark surfaces and light text/buttons — so new CSS must use tokens (including `--glass`/`--glass-strong` for panels over the 3D view and `--wave` for the waveform) rather than hardcoded light colors. The 3D view and LED previews stay dark so saturated color lives in the LED content.
- Type is Sweet Sans Pro (auburn.edu's licensed typeface) when installed, else the system font stack (`--font-ui`, with `--font-display` aliased to it) — no web fonts are loaded, so the app has no network dependencies and works offline for sponsor demos. UI copy is plain sentence case — no all-caps/tracked labels, no monospace labels, no `A // B` or `NAME_V1` styling.
- The sidebar collapses to an icon rail (`.app-shell.sidebar-collapsed`, remembered in `localStorage` as a UI preference only). Every nav item needs a `title` and a `.nav-label` span so the rail stays usable.
